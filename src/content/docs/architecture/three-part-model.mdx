title: The three-part model

zudo-sg's architecture separates three things that are easy to conflate into one project: the components themselves, the applications that consume them, and the tool that catalogs and previews them.

## Components standalone

`@zudo-sg/demo-ui` is a plain Preact component library. It has no dependency on a styleguide, a story format, or a documentation site — importing a button or a card pulls in only the component and its styles. This is what makes the library reusable: any Preact/zfb project can depend on it without also adopting zudo-sg's catalog machinery.

`@zudo-sg/demo-ui` is this site's own example library — it exists to prove the styleguide engine on a real project, and this repository dogfoods its own tooling against it. It is not installed by the engine or by its `new-component` scaffold CLI, and it ships nothing to other projects: adopting the engine never pulls this library in. A components-only package with its stories co-located beside each component — the shape `@zudo-sg/demo-ui` itself uses — is the recommended structure for a project's own component set; see [Adopting the engine](./adopting) for how a project wires its own package in. [zudo-composer](https://github.com/Takazudo/zudo-composer) is a separate project with no coupling to zudo-sg.

## An app uses them

A product application imports components from the library the same way any consumer would — no styleguide-specific wiring required. Several real projects have taken this path independently, which is the original motivation for pulling the shared library out of the styleguide host in the first place: without a clean boundary, every consuming app either duplicated component source or drifted out of sync with it.

## zudo-sg previews them

The styleguide — now the installable `@takazudo/zudo-sg` engine — is a *separate* consumer of the same library. It discovers components through their story files, renders them in a browsable catalog, and provides live preview, design-token tuning, and source-code panels. Nothing about the components themselves depends on the engine; a component library can exist and ship without ever being cataloged.

## Why the split matters

Keeping these three roles distinct is what lets each one evolve independently:

- The component library's public contract is its exports and its story files, not its styleguide page markup.
- An app that consumes the library never has to install or configure the styleguide engine.
- The styleguide engine can be installed into a *different* project than the one that authors the components, previewing a library it does not own.

The rest of this section describes the engine side of that split: what `@takazudo/zudo-sg` owns as an installable package, how it composes into a host's build, and how its preview styling stays isolated from the host's own design system.
