Composer and Sitemapper are standalone products owned by the
[zudo-composer repository](https://github.com/Takazudo/zudo-composer). Use the
[production application](https://zudo-composer.takazudomodular.com/) for both
authoring tools. Their routes, document models, persistence, source generation,
application UI, and deployment permanently belong there. The former in-repo
Composer and Sitemapper applications and their `/composer`, `/composer/preview`,
and `/sitemapper` routes have been removed from zudo-sg.

## What zudo-sg owns

zudo-sg owns the component provider consumed by Composer:

- components and stories in `packages/ui`;
- the twelve co-located `*.composer.tsx` definitions;
- the generated `packages/ui/src/composer-pack.ts` manifest and runtime;
- the explicit `packages/ui/styles/composer.css` stylesheet; and
- provider conformance, boundary, and exact-install verification.

Component definitions use `defineComponent` from
`@zudo-composer/component-contract`. Persisted component ids, schema versions,
field props, and slot ids/props are stable contract keys. Public source metadata
must identify named exports from `@zudo-sg/ui`. Each sidecar exports its display
metadata; the matching story imports and spreads it. Provider code never imports
stories, and stories are not provider inputs.

## Updating the provider

Generate and verify the provider from the zudo-sg repository root:

```sh
pnpm gen:composer-pack
pnpm check:composer-pack
pnpm check:ui-provider-boundary
pnpm test:ui-provider-package
pnpm verify:ui-provider-install -- --exact
```

The immutable package commit and exact Git dependency are recorded in
`ui-provider-handoff.json`. Update Composer to that exact package-only commit;
never use a workspace, file, link, sibling checkout, copied provider, branch,
or moving tag.

There were no users or production Composer/Sitemapper data to migrate. Do not
add redirects, compatibility readers, storage aliases, fallbacks, migration
fixtures, or shims for the removed in-repo applications.
